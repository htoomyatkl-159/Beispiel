## Academic-report alignment

The supplied report requires:

- content-based filtering using numerical audio features and cosine similarity;
- item-based collaborative filtering from a user-song interaction matrix;
- weighted hybrid fusion with content-heavy cold-start behavior;
- like/dislike feedback, playlists, and search-driven recommendations;
- Precision@5 and Recall@5 evaluation when valid relevance data exists.

M00-M01 preserve and package the existing content-based algorithm rather than replacing it. The database and website currently contain only metadata and a tiny 40-song catalog, so collaborative filtering, personalization, and evaluation ground truth are not yet honestly available. The report's stated simulated results must not be presented as measurements of the current web application.

## Catalog-size investigation

The original CSV has 114,000 data rows plus a header. The preserved M01 full artifact contains 89,740 cleaned unique tracks, matching the report supplied by the user. The website database contains 40 rows because M03 deliberately imports the tiny fixture for safe development and contract tests.

Recommended safe expansion:

1. Keep the 40-song database and fixtures for fast tests.
2. Validate and benchmark the prepared development profile (1,000 tracks) before changing the live development database.
3. Import the full M01 artifact only in the later scale milestone, using its manifest and matching catalog version.
4. Start the Python service and API against the exact same catalog version; reject mismatches rather than silently mixing IDs.
5. Back up `api/prisma/dev.db` before any full-catalog import. Never reset or drop it.

## Architecture proposal

Keep the three independent projects:

`app (React) -> api (Express/Prisma) -> recommender (private Python HTTP service)`

The browser should never call Python directly. Express translates its internal track ID to the preserved `sourceTrackId`, calls the private service, validates the catalog/model version, and resolves returned IDs to database metadata. Later user interactions remain in SQLite and feed a separate item-similarity/profile layer; they must not be fabricated for demonstration.

## Roadmap assessment

The existing roadmap fully supports the report. M05-M06 establish the first recommendation request, M07-M09 add authenticated feedback, M10 adds personalization with the existing engine, M11-M12 add playlists/history, M16 adds full-catalog scale and evaluation, and M17 verifies the end-to-end release. The innovative Musical Bridges, Surprise Me, Adventure Level, and legitimate trend-data work in the new request should be added as explicitly approved future milestones after the core recommendation path, not mixed into M05.

## External trend-data recommendation

Do not select a provider until licensing and current API terms are reviewed. Candidate categories for a later investigation are Spotify Charts or another provider with explicit chart redistribution terms, Last.fm API for metadata/scrobble signals, and MusicBrainz for open metadata (not popularity rankings). YouTube/Spotify commercial APIs may restrict caching, redistribution, or require user authorization. Until a source is approved and its terms recorded, Beispiel should show “trend data unavailable” rather than invent rankings.

## API repair and verification

No source-code route repair was required. The API starts successfully with:

```powershell
Set-Location -LiteralPath 'D:\music_recommendation_app\api'
npm run dev
```

Then verify:

```powershell
Invoke-RestMethod -Uri 'http://127.0.0.1:4000/api/v1/health/live' | ConvertTo-Json -Depth 5
Invoke-RestMethod -Uri 'http://127.0.0.1:4000/api/v1/search?q=Comedy&type=track' | ConvertTo-Json -Depth 6
```

Keep that terminal open. If the health request cannot connect, the process is stopped, the port is occupied by another process, or Windows/network policy is blocking loopback. The React app cannot repair a stopped API; start one API process before starting Vite.
